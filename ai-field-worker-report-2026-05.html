AI 工作流观察 · 2026-05-27

过去一个月，普通打工人该关注哪些 AI 变化？

结论先行：最近一个月的关键变化不是“又出了一个更会聊天的模型”，而是 AI 正在变成一层可连接数据、可调用工具、可执行流程、可沉淀方法的工作接口。对市场调研、营销、产品设计和个人生活数据分析来说，这比单点内容生成更值得关注。

覆盖时间 2026-04-27 至 2026-05-27
重点人群 产品经理、市场调研、营销运营、设计师、内容创作者、知识工作者
判断标准 是否连接真实数据、是否进入原工作软件、是否能形成可复用流程、是否有审计和人为把关

一页结论

如果只看热闹，过去一个月全是“agentic AI”。如果看能不能改变普通岗位的日常，真正值得抓住的是下面五个信号。

信号 1

AI 进入办公软件本体

ChatGPT 进入 Excel 和 Google Sheets，Google Workspace 继续把语音、邮件、文档、笔记和个人助理串起来。普通人最直接的变化是：分析、写作、整理和追踪不再总要复制粘贴到聊天框。

信号 2

“技能”变成新的工作资产

GitHub Copilot、Figma、Codex、Claude 等生态都在往 MCP、skills、custom agents 靠拢。一个好 skill 像一份可执行 SOP：告诉 AI 何时用、怎么用、读什么数据、输出什么结果。

信号 3

市场调研开始从项目制走向常驻制

Qualtrics、SurveyMonkey、UserTesting 的共同方向是把问卷设计、样本计划、开放题归因、测试脚本、洞察摘要和建议输出串成连续流程。研究员的角色会从“亲手做每一步”转向“定义标准并验收”。

信号 4

营销从“生成内容”转向“编排体验”

Adobe、Google、YouTube 等方向都指向同一件事：不只是生成海报或文案，而是根据品牌规范、用户分群、实时数据和渠道表现来持续调整内容与体验。

信号 5

生活数据也开始 skill 化

本地的微信读书 skill 已经不是简单提示词，而是带鉴权、接口、字段规范和深度链接的个人阅读数据入口。Steam 还没有同等官方 AI skill，但已有 Web API 足够支撑一个“游戏库分析 skill”。

反向提醒

突破不等于放心托管

Agent skills 的供应链和语义投毒风险在上升。能安装不代表能正确运行，能运行不代表输出可靠。越是连真实数据和写操作，越需要权限边界、样本校验、来源追踪和人工审批。

过去一个月值得关注的事件

以下不是完整新闻清单，而是按“对普通岗位是否有迁移价值”筛选后的事件。

4/28

Anthropic 推出面向创意工作的 Claude 连接器

Claude 开始更明确地连接设计、3D、音乐等创意工具；Claude Design 也强调从品牌、设计系统、原型、PPT、营销物料到 Canva/PPTX 导出的流程。对产品经理和营销人来说，它的启发不是“AI 会画图”，而是“AI 能读取品牌与设计上下文后持续迭代”。

突破性判断：中 对非设计背景的人非常有用，但专业交付仍要靠设计判断、版权判断和品牌一致性审查。

5/04

Adobe Research 总结 Summit 2026 的代理式营销与体验编排

Adobe 展示了 Proactive Insights、Root Cause Analysis、Brand Intelligence、CX Enterprise Coworker、Project Face Off 等方向：自动发现业务异常、解释原因、维护品牌一致性、用 AI persona 预演 A/B 测试。

对普通岗位：这类能力短期更偏企业级，但它会下沉为市场运营的标准能力：自动发现转化率下滑、解释哪个人群/素材/渠道出了问题、给出下一步实验建议。

5/05

ChatGPT 强化记忆来源，并进入 Excel 和 Google Sheets

OpenAI 发布的 ChatGPT 更新包括更可见的 memory sources，以及 ChatGPT for Excel and Google Sheets。前者让个性化回答开始有来源可查，后者把公式、清洗、多表、情景分析、预算、tracker 等任务直接放进表格侧边栏。

对市场调研：开放题主题归类、问卷数据交叉分析、漏斗表清洗、竞品价格表比较都可以在表格里完成初稿。风险：公式、统计推断、样本口径必须复核。

5/06

GitHub Copilot 在 VS Code 增强 agent、skill 和浏览器/终端上下文

Copilot 可用自然语言生成 custom agents、skills 和 instructions；agent 可读取浏览器标签、读写已打开终端、远程监控 CLI 会话。对开发者是效率升级，对普通业务岗位的启发是：未来很多“团队方法论”会以 markdown skill 的形式版本化、复用和审查。

突破性判断：高 不是因为它会写代码，而是因为它把“工具权限 + 工作方法 + 审查日志”放进同一套工作台。

5/11

Qualtrics 提出 agentic market research：从问题到决策答案

Qualtrics 描述的目标是：业务问题触发 agent，agent 制定研究计划、选择方法、连接人类和合成样本、输出面向决策的建议。它特别强调 MaxDiff、conjoint 等复杂方法可被嵌进对话式工作流。

反思：这是研究流程自动化的重要方向，但“合成样本”只能降低探索成本，不能替代真实用户证据。最危险的是把看起来严谨的模拟结果当成真实市场。

5 月

SurveyMonkey 把 AI 问卷创建、项目化追踪和品牌样式合并到产品更新

用户可以描述目标生成问卷，也可以把相关问卷连接成 Programs 来追踪趋势，并用 AI 生成品牌样式。对中小团队来说，这比“请 AI 写 10 个问题”更实际，因为它开始把反馈采集变成连续项目。

突破性判断：中 提效很明显，但方法质量取决于问题定义、样本选择和是否避免诱导性问题。

5/19

Google I/O：Search agents、AI Studio、Stitch、Workspace 进入代理式阶段

Google Search 宣布 information agents，用于持续监控指定问题；AI Studio 接入 Workspace 数据并增强 app 视觉定制；Stitch 支持实时设计迭代并导出到 Antigravity；Workspace 方向则把语音、Gmail、Docs、Keep、Gemini Spark 连接到个人和工作任务。

对普通人：竞品监控、行业动态追踪、信息源聚合、内部数据仪表盘、低代码原型都更容易启动。风险：平台替你筛选信息，可能削弱原始来源核查。

5/20

Figma 发布 code-to-canvas 工作流：MCP、skills、写入画布

Figma 的 May 2026 release notes 解释了 agents、MCP、skills、write to canvas，并演示从代码到画布、从画布到代码的工作流。对产品设计的影响是：设计稿、组件、代码和 agent 指令之间的边界继续变薄。

反思：这不是“设计师被替代”，而是设计师需要更会维护组件语义、交互状态、可访问性和设计系统上下文。

5 月

UserTesting 的 AI 零售体验报告提醒：AI 功能上线后仍大量返工

UserTesting 报告显示，零售团队在 AI 体验上投入很快，但消费者真正要的东西和企业优先级并不总一致。报告里一个值得警醒的数字是：很多 AI-powered digital experiences 上线后仍需要大量修订。

对产品团队：AI 功能不应只测 prompt 是否成功，还要测用户是否信任、是否理解、是否愿意在关键流程里使用。

三个工作场景的可落地变化

场景 过去常见做法 现在更值得尝试的 AI 工作流 不要被什么迷惑
市场调研 研究员排期、手写问卷、外部发样本、人工清洗开放题、PPT 汇报。 业务问题先转成研究 brief；AI 生成问卷初稿和抽样假设；用表格 AI 做清洗和交叉；用 UserTesting/SurveyMonkey/Qualtrics 类工具做摘要、主题和建议；最后由研究员验收方法和结论。 “合成样本几小时出结果”不等于市场真实反应。它更像低成本预研和方案压力测试。
市场营销 内容团队按渠道产出素材，投放后再看报表，异常原因靠人工拆解。 品牌规范、素材库、CDP/CRM、渠道表现接入 agent；自动发现转化异动；生成受众解释、素材变体和实验建议；人工批准后上线。 “自动生成 100 张图”价值有限。真正有价值的是素材是否符合品牌、是否对应人群、是否能形成可解释实验。
产品设计 PM 写 PRD，设计师出 Figma，工程师再实现，用户测试经常滞后。 用 Claude Design/Stitch/Figma MCP 生成多方向原型；从 Figma 发起测试脚本；把用户反馈、开放题、会话视频摘要回流到设计决策；用 design system skill 固化组件规则。 AI 生成界面经常“看起来像产品”，但交互状态、边界条件、可访问性和错误流程仍要人负责。

关于 GitHub 上的 user research skill

你举的“从调研问卷设计到数据分析全流程自动化的用户研究 skill”方向已经有雏形，但要分清两类东西：一类是方法型 skill，负责让 AI 按研究方法输出；另一类是数据接口型 skill，负责读取真实系统数据。

已有雏形

公开目录里已经能看到 user-research-analysis、user-research-synthesis、ux-researcher、data-analyst 等 skill。它们通常会定义输入、研究方法、主题归纳、证据引用、优先级和建议输出。

这对普通团队已经有用：可以把访谈记录、问卷开放题、客服反馈、App Store 评论放进去，要求按固定框架输出“主题、证据、影响、建议、优先级”。

还不等于全流程自动化

真正的全流程需要再补四块：样本招募或面板接口、问卷平台接口、数据清洗和统计校验、结果回写到 Notion/Jira/Figma/Slides。仅有 SKILL.md 更像方法说明书，不是完整业务系统。

更严肃的做法是把 skill 写成“方法 + 接口 + 输出验收标准”：比如要求标注样本量、置信限制、不可推广范围，并列出需要人工复核的统计结论。

安全和质量判断：最近的 agent skills 研究提示，SKILL.md 不是被动文档，而是会影响 agent 发现、选择和执行的“操作性文本”。公开技能库里还存在安装成功但运行错误、输出不可靠、权限过宽、语义诱导等问题。普通用户安装第三方 skill 前，至少要看三件事：是否需要 API key 或本地文件权限、是否有可复现测试、是否明确禁止上传敏感数据。

微信读书 skill 的本质：数据接口 + 代理说明书

我检查了本地已安装的微信读书 skill。它不是单纯提示词模板，而是通过 POST https://i.weread.qq.com/api/agent/gateway 调用微信读书相关接口，并用 WEREAD_API_KEY 鉴权。它支持搜索、书架、阅读统计、笔记划线、热门划线、书评、推荐等能力，还规定了字段解释、分页、时间戳展示、深度链接格式。

为什么这有启发

它把个人数据变成 AI 可读、可解释、可跳转的结构化上下文。AI 不再只是问“你最近读了什么”，而是可以读取书架、阅读时长、笔记、划线和书评，再生成阅读偏好、复盘和推荐。

它不只是“开放 API”

更准确地说，它是受控的 Agent API Gateway 加 skill 规范。API 解决“取数”，skill 解决“什么时候取、怎么解释、怎么展示、哪些字段不能猜”。

可迁移模式

任何个人内容平台都可以照这个模式做：先定义鉴权和接口，再定义字段口径、隐私边界、输出模板、深度链接。读书、游戏、影视、健身、消费账单都适用。

Steam 有没有类似微信读书的 AI skill？

短答：截至 2026-05-27，我没有查到 Valve/Steam 官方推出类似“微信读书 skill”的 AI 数据开放 skill。Steam 有官方 Web API 和 OpenID，足够你参考微信读书 skill 的形态开发一个“Steam 游戏库分析 skill”，但它不是现成的官方 AI agent gateway。
可用能力 Steam 官方能力 可做出的 AI 分析 限制
身份确认 Steam OpenID 可验证用户 SteamID，不需要用户把密码交给你。 让用户登录后自动加载自己的游戏库。 OpenID 主要是身份确认，不是完整 OAuth 授权体系。
游戏库 IPlayerService/GetOwnedGames 返回可见游戏库，可包含名称、icon、游玩时长、免费游戏等。 游戏库结构、沉没成本、未玩清单、时长分布、偏好聚类、年度报告。 只有在用户游戏详情对你可见时才返回；私密资料无法分析。
近期游玩 GetRecentlyPlayedGames 可取近期游玩记录。 最近兴趣变化、短期推荐、重新捡起哪些游戏。 时间窗口有限，且取决于 API 可见性。
成就和统计 ISteamUserStats 提供部分游戏成就和统计能力。 完美主义倾向、成就党/体验党判断、续玩建议。 不同游戏支持程度不同，部分数据需要 app 级权限或公开状态。
推荐 Steam 自身有推荐系统，但 Web API 不是“个人推荐 API”。 你可以基于用户库、时长、标签、愿望单或商店元数据自建推荐。 官方 API 对商店标签、价格、评论等元数据覆盖有限，可能需要额外数据源并遵守条款。

一个可行的 Steam skill 设计

name: steam-library-analyst
description: 读取用户授权或公开的 Steam 游戏库，分析偏好、沉积游戏、游玩节奏，并给出可解释推荐。

required_env:
  - STEAM_API_KEY

workflow:
  1. 接收 Steam profile URL、vanity name 或 SteamID64
  2. 必要时用 ResolveVanityURL 转成 SteamID64
  3. 用 GetOwnedGames(include_appinfo=true, include_played_free_games=true) 读取游戏库
  4. 用 GetRecentlyPlayedGames 读取近期兴趣
  5. 可选：读取成就、全局成就比例、商店元数据或用户自填标签
  6. 输出：
     - 游戏偏好画像
     - backlog 分层
     - “今晚玩什么”推荐
     - “值得重开/值得放弃/适合碎片时间”的解释
     - 隐私和数据缺口说明

guardrails:
  - 不绕过私密资料
  - 不存储用户明细，除非用户明确同意
  - 不用于未请求营销
  - 不提供多人游戏作弊或不公平优势建议

开发难度不高，难点不在 API 调用，而在推荐解释和数据补全。Steam API 能告诉你“拥有什么、玩了多久、最近玩什么”，但未必直接告诉你“为什么喜欢”。要做得像微信读书 skill 一样好，需要把游戏类型、标签、价格、评价、发售年份、平台兼容性、多人/单人属性等元数据补齐，并把推荐逻辑写成可审查的规则。

是否真的是突破？

是真的突破的部分

  • AI 从“回答问题”走向“接入数据后执行流程”。
  • 办公软件、设计工具、代码工具开始允许 agent 读上下文、写回结果、持续运行。
  • skill/MCP/connector 让个人和团队的工作方法可以被打包、版本化、复用。
  • 市场调研、营销和产品设计这类过去高度依赖经验的流程，开始被拆成可编排模块。

还不是突破的部分

  • 很多“agent”本质上仍是任务自动化加漂亮包装。
  • 没有真实数据、没有权限管理、没有回写、没有验证的 AI，仍只是增强版问答。
  • 合成用户、AI persona、自动 A/B 预演只能降低探索成本，不能替代真实行为证据。
  • 第三方 skill 生态缺少足够的质量、权限和供应链治理。

我的判断：这轮变化对普通打工人的意义，不是“每个人都要会训练模型”，而是每个人都要学会把自己的工作拆成数据源、判断标准、可复用流程和人工验收点。未来的职业优势更像“会设计和管理 AI 工作流”，而不是“会问 AI 一个好问题”。

普通打工人下周可以做什么

  1. 列数据清单：你工作里有哪些数据可以导出或通过接口读取？表格、问卷、CRM、用户访谈、Figma、客服记录、竞品网页、阅读笔记、Steam 游戏库都算。
  2. 写一个小 skill：不用一开始就接 API。先写清楚触发场景、输入格式、分析方法、输出模板、不能做什么。
  3. 把 AI 放回原工具：如果数据在表格里，就优先用表格侧边栏或脚本；如果设计在 Figma，就优先用 Figma MCP/插件；不要每次都复制到聊天框。
  4. 建立验收清单：任何 AI 研究结论都要标样本量、数据来源、不可推广范围、异常值、人工复核项。
  5. 优先做低风险流程：先自动化摘要、归类、初稿、监控和提醒；涉及发邮件、改价格、删数据、发布内容时保留人工审批。
